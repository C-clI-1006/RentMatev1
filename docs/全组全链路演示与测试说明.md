# RentMate 全组全链路演示与测试说明

ELEC5620 Stage 2 | 小组联调版 | 2026-10-30

## 01 使用范围与验收口径

本说明用于各成员在自己的 Mac 或 Windows 电脑上启动、演示和检查完整业务链路。主业务页面是 /app；/demo 是保留的技术验收面板。无需打开 Swagger，也不需要前端构建工具。

当前版本已验证：后端 456 项测试通过；浏览器 Full System Check 为 13/13 PASS；真实 campus-qwen 的消息分类、维修评估、发票分类和月报正文四条链路通过。以上是当前开发环境的证据，每位成员仍须在自己的电脑重测。

| 检查对象 | 已验证结果 | 不可扩大解释 |
| 后端与集成检查 | 456 passed；13/13 PASS | 不保证所有学校电脑环境相同 |
| 真实模型 | 四条代表性业务链路通过 | 不代表所有自然语言输入都正确 |
| 通知 | 本地收件箱、审批与幂等有测试 | 不代表真实邮件或短信投递 |
| Windows 定时任务 | 已检查脚本并准备验收步骤 | 尚未在真实 Windows 上执行 |

## 身份令牌速查

| 使用位置 | Property context | 填入的演示令牌 |
| Session settings - Tenant | demo-property | tenant-demo |
| Session settings - Property manager | demo-property | manager-demo |
| 另一物业经理 | demo-property-2 | manager-other-demo |
| AI settings / Local operations | 使用独立操作权限 | scheduler-demo |

这些令牌仅用于本地演示。学校 API key 是另一种密钥，不能填入 Session token。下拉框切换角色只改变界面，不授予权限；后端仍验证令牌和物业绑定。

## 建议演示顺序

启动并配置真实模型 -> 上传证据 -> 租客消息与维修登记 -> 经理评估和状态流转 -> 证据分类审核 -> 租金/租约扫描 -> 回复审批与投递 -> 租客收件箱 -> 月报与历史 -> 时间线与技术验收。

## 02 在自己的电脑启动

### Mac 一键启动

先安装 Python 3.11 或更新版本。进入项目目录后运行：

```sh
bash Start-RentMate.sh
```

也可以在 Finder 中双击 Start-RentMate.command。如果系统限制执行，回到终端运行上面的 bash 命令。首次启动会创建 .runtime/.venv，并在缺依赖时安装 backend/requirements.txt。

启动后打开 http://127.0.0.1:8020/app。终端需保持运行；Ctrl+C 停止服务器。已有 8020 服务时可另选端口：

```sh
bash Start-RentMate.sh --port 8021
bash Start-RentMate.sh --no-seed
```

默认启动会初始化演示身份，并重置固定演示审核项及租金/租约提醒练习。已准备好演示状态时，使用 --no-seed，避免重新初始化固定练习。动态创建的真实演示记录不会被脚本整体清空。

### Windows 启动

```powershell
.\Start-RentMate.cmd
```

同样打开 http://127.0.0.1:8020/app。若 PowerShell 被限制，可在终端使用：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File .\Start-RentMate.ps1
```

### 本地数据与隔离

本地数据库为 .runtime/rentmate-demo.db，原始文件放在 .runtime/evidence。不要提交数据库、.env、真实 API key 或浏览器凭据。当前开发预览的 8024 端口是临时环境，不是全组固定入口。

建议业务演示与 /demo 技术检查分开准备数据。已审批的提醒不再出现在待审核队列，直接在同一已操作数据库上重跑技术面板可能不符合其初始状态预期。可在另一份干净项目目录中启动技术验收。

## 03 配置真实 Campus Qwen

1. 连接学校要求的网络或 VPN。打开页面右上角 AI settings。
2. Local operations token 填 scheduler-demo，点击 Load current settings。
3. API base address 填学校给的地址；当前课程示例为 http://10.167.60.148:8000/v1。地址、模型名以学校实际提供的信息为准。
4. Model name 填 campus-qwen；API key 填自己的有效学校密钥。
5. 点击 Apply settings，再点击 Test model connection。

成功提示应包含 Real model returned a validated response、source=llm。这表示一次真实请求及响应校验成功，不表示所有业务功能自动验收通过。

| 设置行为 | 实际含义 |
| Apply settings | 应用配置，不会自动验证模型 |
| Test model connection | 发送无敏感数据的问候并验证响应 |
| API key 输入框清空 | 正常保护行为，不代表密钥丢失 |
| 读取配置只显示 configured | 后端不会把密钥返回浏览器 |
| Restore startup settings | 丢弃内存覆盖，恢复环境配置 |

配置仅保存在当前服务器进程内，重启后需重新输入，或使用本机 backend/.env。单独运行的月报进程不会继承网页内存设置，必须从自己的环境或 backend/.env 读取配置。更换 API 地址时必须重新输入密钥。

### 模型不可用时的正确表现

未配置时，Communication 可进入明确标注的关键词模式；维修可能 under_review；文档可 saved 但分类 failed；月报可保留结构化数据而正文 missing。不得把这些降级路径说成真实 Qwen 成功。

### 接口返回 502 时

检查网络/VPN、地址是否包含正确的 /v1、模型名和密钥是否有效。502 也可能表示响应格式不符合契约，不能直接断言一定是 VPN 故障。不要把真实密钥发到群里或截图里。

## 04 证据上传与租客消息

### A. 先上传一份可复用的证据

1. Session settings 选择 Tenant，填 demo-property、tenant-demo。
2. 打开 Documents，选择项目内 demo/samples/test-invoice.pdf，点击 Upload document。
3. 打开真实保存的记录，记下 Document ID。后续 evidence_refs 使用这个不透明 ID，不使用文件路径或自己编造的编号。
4. 区分 Upload=saved、Classification=classified/failed、Association=associated/unassociated。三种状态互不等同。

真实模型验收样例：该 PDF 被识别为 invoice，持久化 source=llm、confidence=0.99。界面不一定暴露原始分类建议或模型来源；不得从文件名在前端猜测分类。

### B. 租约问题分类

打开 Messages，提交：

```text
When does my current lease end?
```

记录真实 Message ID、reply_status 和 delivery_status。当前消息提交 API 不返回原始分类字段，网页标记 unavailable 是诚实限制，不是允许前端推断。已验收案例的实际保存分类为 lease_rent，并创建 pending_review 草稿。

### C. 紧急消息与审批保护

```text
There is a strong smell of gas in my kitchen.
```

预期：维修意图被识别；可通过保存的 message_id 关联到准确维修单；emergency_flag=true、priority=emergency；回复保持 pending_review、not_dispatched。经理告警 accepted 只表示入队，不表示已收到。

页面不得根据输入文字自行推测 emergency 或 classification，也不得拿任意最新维修单冒充关联记录。Messages 的会话回执是临时展示，切换身份或刷新后可能清除；真实业务记录仍在后端。

不要重复点 Submit。页面阻止同一表单并发重复提交，但 Communication 没有 HTTP 幂等键；主动再次提交仍会产生新消息。

## 05 维修登记、评估与闭环

### 租客登记普通维修

在 Maintenance 输入以下内容，证据栏填写第 04 页上传返回的 Document ID：

```text
Title: Loose kitchen cupboard handle
Description: The cupboard handle is loose but usable.
No injury or immediate danger. Please arrange a routine repair.
Location: Kitchen
```

预期返回真实 Request ID。模型正常时可为 assessed、routine；不确定或失败时 under_review 是有效安全降级，不得显示为自动批准。查看 Request history 中的来源信息；真实模型样例记录 source=llm、confidence=0.95。

### 经理推进状态

切换 Property manager，令牌 manager-demo，物业 demo-property。按标题和准确 Request ID 打开刚创建的维修单，不要误操作其他人的演示记录。

| 当前状态 | 演示操作 | 预期结果 |
| submitted / under_review | Manual assessment，填 priority 与 rationale | assessed，版本递增 |
| assessed | Update status 选择 approved，填写 reason | approved |
| approved | 选择 in_progress，填写 reason | in_progress |
| in_progress | 选择 awaiting_confirmation，填写 reason | awaiting_confirmation |
| awaiting_confirmation | 选择 closed，并提供有效证据 ID | closed |

每一步都使用刚读取的实际版本。后端决定状态是否合法，不能靠前端选项绕过。closed 需要存在且属于正确物业的证据；只上传一个文件并不等于自动完成关闭证据校验。

### 必测失败路径

- 从不允许的状态直接 closed：应被后端拒绝，不能伪装成功。
- 空 reason 或关闭时缺证据：应显示验证错误。
- 使用过期版本：应出现 409，刷新并重新打开记录后再操作。
- 跨物业或不存在的证据 ID：应拒绝，不能记录为成功关联。

每个经理动作后检查新状态、版本和 history。不要为了继续演示删除失败记录或弱化断言。

## 06 两种审核与通知闭环

### 文档分类审核

经理打开 Documents & Evidence，选中上传的文件。选择 confirm_suggested 可确认已有有效建议；模型失败或需改正时，用 select_category 并选 invoice 等契约允许的分类。保存后检查 final_category、reviewed_by、reviewed_at。

文档分类审核不是租客回复审批。不要把 Evidence 的操作改成臆造的 approve/reject。

### 租金与租约提醒

1. 经理进入 Lease & Rent，在 Local operations 使用独立 scheduler-demo 凭据运行 Run rent & lease scan。
2. 查看真实 candidates、drafts_created、drafts_reused。重复同一提醒来源应复用，不应产生重复草稿。
3. 在 Review Centre 查看来源、理由、草稿正文和版本。
4. 编辑并批准一个 rent reminder；为另一个 lease deadline 填原因并 Reject。
5. 审批结果应分别为 approved / rejected。批准只是使准确版本进入后续投递流程，拒绝不得产生租客消息。

当前没有通用租金台账列表 API。Lease & Rent 展示提醒工作流与真实来源，不在前端计算欠款或编造账目。

### 投递与收件箱

在 Local operations 先运行 Handoff maintenance updates（需要展示维修状态回复时），再运行 Dispatch queued notifications。检查实际 delivered、pending_retry、failed 等数量。

切换 Tenant，打开 Notifications。找到批准后编辑过的准确内容和 delivered_at；拒绝的提醒不得出现。重复 dispatch 不应为同一 event_id 和 recipient_id 再生成一条收件箱记录。

| 状态 | 可以对老师说什么 |
| auto_eligible | 符合自动回复条件，尚不证明已投递 |
| pending_review | 仍需经理决定，尚未获批 |
| accepted / queued | 已入队，不代表送达 |
| delivered | 记录了本地收件箱投递成功 |
| failed / pending_retry | 失败或等待重试，不能说已发送 |

已修复的安全回归：入队后撤销 tenant_property 绑定，dispatcher 必须阻止投递、记录 failed 和授权拒绝审计。该场景有自动化测试；不要通过浏览器自行改数据库演示撤权。

## 07 月报、提前触发与时间线

### 经理按月生成报告

1. Manager -> Reports，选择当前授权物业与月份。
2. 点击 Generate report，检查实际 report_id、outcome、data_as_of 和各结构化部分。
3. 单独查看 Narrative。真实验收应有非空正文，且 narrative.source=live；不要把结构化汇总当作 LLM 正文。
4. 回到 Report history，重新打开同一个 report_id。Generate 在本会话同一月份复用幂等键；只有 New generation 明确生成另一版本。

部分数据缺失允许 partial_success，并标明缺失；三源全部不可用应停止且不保存报告。正文失败时保留已算好的结构化数据并标记 missing。选中记录后展示生成时的最新状态，不承诺历史时点完整快照。

### 不等月初，立即触发同一个任务

Mac：

```sh
bash Start-RentMate.sh --monthly-run --no-seed
```

Windows：

```powershell
.\Run-Monthly-Reports.ps1
# 如需指定月份验证：
.\Run-Monthly-Reports.ps1 -Year 2026 -Month 9
```

默认按 Australia/Sydney 选择上一个日历月，日志时间仍为 UTC。例如 2026-10-30 执行默认选择 2026-09；悉尼 11 月 1 日 02:00 应生成 10 月，而不是受 UTC 日期影响生成 9 月。

同一调度月份重试会复用稳定报告 ID。日志写入 .runtime/monthly-report-runs.jsonl，检查 period、business_timezone、succeeded、failed、report_id、reused。手动运行通过不证明操作系统会自动唤起。

### 自动运行与时间线

Windows 可使用 Register-Monthly-Reports.ps1 注册每月 1 日 02:00；要求系统时区 AUS Eastern Standard Time。Windows 实机唤起、任务账户和退出码仍需全组现场验收。Mac 的 --monthly-run 仅立即执行，不安装 launchd/cron。

Activity Timeline 选择准确维修单，分别查看 Maintenance history 与 Evidence timeline。事件必须能对应实际 ID。没有通用全局事件 API，不要把所有最新记录拼成假关联。Guided Workflows 用于引导演示，Pending 步骤不会自动完成。

## 08 全组测试记录与现场排错

### 各成员最低验收项

| 模块 | 必做操作 | 记录证据 |
| Communication | 普通租约问题、燃气味、未知意图 | message_id、reply/delivery 状态 |
| Maintenance | 登记、评估、完整流转、无证据拒绝 | request_id、版本、事件历史 |
| Evidence | PDF 上传、分类审核、维修证据关联 | document_id、来源、final_category |
| Lease & Rent | 扫描两次、审批一个、拒绝一个 | 来源、draft_id、复用数量 |
| Reporting | 生成、历史读取、同键重试、缺正文 | report_id、source、outcome |
| 共享权限与投递 | 跨物业拒绝、无审批不发、重复不重投 | HTTP 状态、event_id、收件箱 |

每条测试请记录：测试人、电脑/系统、分支与 commit、开始时间、输入内容、准确后端 ID、预期结果、实际结果、是否 PASS、截图或日志路径。截图必须遮住真实 API key。

### 自动验收入口

```sh
# Mac：不启动服务器，只跑确定性与集成检查
bash Start-RentMate.sh --verify --no-seed
# 可选真实 Maintenance 验收，需要环境或 .env 配置
bash Start-RentMate.sh --verify --live --no-seed
```

Windows 可用 Start-RentMate.ps1 -Verify。另在干净演示数据上打开 /demo，点击 Run full system check，检查 13 个 PASS、0 个 FAIL。面板通过不等于真实模型已验证；四条模型链路应单独记录来源。

| 错误/现象 | 排查方法 |
| 401 / 403 | 令牌、角色和物业是否匹配；操作入口是否需要 scheduler |
| 404 | 可能不存在，也可能是跨物业隐匿；不要推断记录泄漏 |
| 409 | 版本过期或幂等冲突；刷新准确记录再重试 |
| 422 | 阅读原因、证据或请求字段验证错误 |
| 模型 502 / missing | 检查网络、配置和输出格式，保留真实失败状态 |
| 上传成功但分类 failed | 原文件仍保存；走分类人工审核 |
| 草稿在但收件箱为空 | 待审核、未 dispatch、投递失败都可能；不能猜已送达 |
| 端口已占用 | Mac 用 --port 8021，或先停止自己的旧服务 |

## 09 现场演示节奏与证据归档

### 建议 12-15 分钟演示安排

| 时间 | 演示内容 | 必须展示的证据 |
| 0-2 分钟 | 启动、身份与真实 API 测试 | 当前物业、角色、validated response |
| 2-5 分钟 | 上传证据、普通维修与经理流转 | document_id、request_id、版本和 source |
| 5-8 分钟 | 租金/租约提醒、批准与拒绝 | draft_id、来源事实、两种决定 |
| 8-10 分钟 | 通知投递与租客收件箱 | 准确内容、delivered_at、无重复 |
| 10-12 分钟 | 月报生成、历史和时间线 | report_id、live/missing、事件 ID |
| 12-15 分钟 | 紧急审核阻断与验收总结 | pending_review、not_dispatched、测试记录 |

### 测试记录模板

| 字段 | 小组填写内容 |
| 测试人 / 系统 / 时间 | 填电脑系统版本与本地时间，注明时区 |
| 代码版本 | git branch --show-current 与 git rev-parse --short HEAD |
| 测试用例与输入 | 原样记录英文消息、月份、理由和使用的证据 ID |
| 身份与物业 | 只记录演示身份标签，不记录真实 API key |
| 真实业务 ID | message / request / document / draft / event / report |
| 预期与实际 | 状态、版本、LLM 来源、是否发生投递 |
| 结果与证据 | PASS / FAIL / UNVERIFIED，截图和日志路径 |

出现失败时不要只写“不能用”。提供复现路径、准确 ID、实际状态与错误码，并说明是否可以重试。若没有在该电脑上执行，填写 UNVERIFIED，不得沿用其他成员的 PASS。

### 演示结束前

确认五个 Agent 都出现过；把结构化规则与真实 LLM 输出分开讲；展示至少一个审核阻断和一个授权拒绝；保留报告、草稿和证据 ID。不要承诺尚未实测的 Windows 自动唤起、真实邮件短信或所有模型输入都成功。
